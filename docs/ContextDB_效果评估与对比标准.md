# ContextDB 效果评估与对比标准

日期：2026-09-20 · 适用范围：企业与团队 Agent、workspace 归属、Memory + Knowledge

本方案配套 [V3.1 详细设计](ContextDB_详细架构设计_V3.1.md)。本文给出评测协议和验收建议，尚未运行本项目与任何竞品的对比实验，不含实测排名。

## 1. 评估要回答什么

需要分别回答四个问题：能否找到正确证据、能否正确管理随时间变化的记忆、是否提高 Agent 的实际任务成功率、付出的成本和运行复杂度是否值得。

不能只用数据库 QPS、公开问答榜单或“支持图谱”等功能数量判断效果。对于当前系统，未确认候选、越权资料或已撤回事实即使能提高某些问答题的分数，也不应进入正常上下文。

采用两阶段判断：先通过企业正确性门槛，再比较质量—延迟—成本。公开记忆 benchmark、检索指标和企业特定场景分别使用，不把它们混成一个缺少解释的总分。

## 2. 对比对象及身份

| 对象 | 本次已知状态 | 处理方式 |
| --- | --- | --- |
| 本仓库 ContextDB V3.1 | 架构设计，未发现业务实现 | 当前可检查设计覆盖；上线能力必须由原型验证 |
| Cognee | 已核查官方架构、recall 文档和公开评测报告 | 固定 OSS 版本、检索模式、后端与模型后运行 |
| 用户提及的“rds contextdb” | 具体项目尚待全名或链接确认 | 保留待测项，不假定是云数据库或某个同名项目 |
| 无记忆 Agent | 基线 | 固定模型与工具，关闭外部上下文 |
| 简单混合检索 | 工程基线 | 同一 PG 上的关键词+向量+基础融合 |
| 正确证据输入 | 诊断用对照 | 给同一回答模型必要的金标准证据，不作为可部署竞品 |

Cognee 的官方架构包含关系、向量与图相关能力，recall 提供多种查询路径；应记录实际启用的模式，而不是把其某个模式当作整套系统。[Cognee 架构](https://docs.cognee.ai/core-concepts/architecture)、[Recall 文档](https://docs.cognee.ai/core-concepts/main-operations/recall)

开源与商业配置分别列行，不能用 OSS 成本配商业功能。对不具备某个企业能力的产品，记录“原生不支持”或“尚未核验”；若加适配层补齐，则形成独立的“产品+适配层”配置，并计算适配成本。

## 3. 六类核心指标

| 维度 | 主要指标 | 测量对象 |
| --- | --- | --- |
| 检索质量 | Evidence Recall@k、nDCG@k、Evidence Coverage@B、空命中/误命中率 | 找到了哪些必要证据，是否在 token 预算内 |
| 记忆质量 | 候选抽取精确率/召回率、当前事实正确率、时间查询正确率、冲突处理正确率 | 新增、更新、确认、过期和冲突 |
| Agent 效果 | 任务成功率、事实错误率、引用支持率、无答案处理、人工返工率 | 完成真实业务任务的表现 |
| 企业正确性 | workspace 泄露、候选泄露、撤回残留、版本混淆、重复发布 | 数据是否在正确状态和范围内使用 |
| 性能可靠性 | 查询 p50/p95/p99、吞吐、排队、发布延迟、失败率、恢复耗时 | 真实 API 与后台链路 |
| 总体成本 | 导入/增量/查询费用、基础设施、审阅时间、接入与维护成本 | 每千次查询和每个成功任务的总成本 |

### 3.1 检索口径

Evidence Recall@k 为“返回的相关证据单元数 / 标注的必要证据单元数”，按问题求值后汇总。证据单元使用稳定的源文档版本、页码/段落或事件 ID，不直接使用某个系统内部 chunk ID，否则不同分块方案不可比。

Evidence Coverage@B 在统一 token 预算 B 下测量必要证据覆盖，并额外报告需要多条证据的题目是否完整覆盖。图路径、摘要和文本片段均需映射到可核验来源；无来源映射时仍可测答案，但该项标记无法测量，不能凭摘要文字相似就判定来源正确。

无答案问题没有必要证据集合，不参与 Recall 分母；单独测误召回、错误作答和正确拒答。对可回答题测不必要拒答，防止系统靠全部拒答获得低错误率。

### 3.2 记忆与回答口径

候选抽取的精确率关注候选是否被原文支持，召回率关注符合预定记忆策略的事实是否被提取。标注策略和“重要事实”定义在测试前固定，不能把所有原文句子都作为应抽取记忆。

当前事实正确率按查询时刻的有效版本判断；历史问题按目标时刻判断。已提出但未确认的变更不能当作新事实。冲突题不能仅检查是否出现了新值，还要核对该值是否有有效确认与适用范围。

引用支持率按回答中的实质性主张逐条检查证据是否支持；引用覆盖率检查哪些需证据的主张缺少引用。答案正确但引用错版本，两个指标分别记录，不能判为完全通过。

任务成功优先由可执行业务断言或盲审确定；纯文字任务可由固定 rubric 的 LLM judge 辅助，并对争议项和抽样结果人工复核。裁判不接收系统品牌，版本、prompt、评分日志均保留。

## 4. 企业场景硬门槛

以下是本项目验收要求，不是宣称行业存在统一认证。门槛失败时可以继续报告质量分数用于研究，但不能用高平均分抵消生产适配失败。

| 门槛 | 场景 | 通过条件 |
| --- | --- | --- |
| G1 空间隔离 | 两个 workspace 具有同名项目和相反配置 | 授权测试集中无跨空间正文、引用、文件或任务信息泄露 |
| G2 候选隔离 | 自动抽取一个高置信度但未确认决策 | 普通 search/get/resolve 不把它当作已发布记忆 |
| G3 确认有效性 | 确认前后修改候选或来源 | 过期确认不能授权新内容发布 |
| G4 来源撤回 | 撤回支持某记忆的文档 | 在定义的提交/授权边界后，新读取不返回受影响内容 |
| G5 冲突管理 | 重要决策出现互斥新值 | 未确认前不覆盖旧有效事实；确认后按规则切换 |
| G6 幂等发布 | 响应丢失、并发重试、Worker 强退恢复 | 不产生重复逻辑事件或多次业务发布 |
| G7 可追溯性 | 根据返回引用读取原始版本 | 来源确实存在、版本匹配、权限有效 |
| G8 预算与错误契约 | 极小预算、依赖失败、无答案 | 不突破声明预算；不伪装完整成功 |

报告写“在 N 个用例、M 次执行中观察到 0 次泄露”，不能写成数学上的零风险保证。需要覆盖并发、缓存、历史版本和错误信息，不能只测一个 happy path。

## 5. 企业评测集

建议先构建 300 个质量用例和独立的治理/故障测试集作为启动规模；不是最终统计充分性的保证。

| 类型 | 初始题量 | 示例 |
| --- | --- | --- |
| 精确事实与文档定位 | 60 | 某项目负责人、发布规则、文档原页码 |
| 中文同义问法与领域术语 | 40 | 缩写、产品代号、口语化提问 |
| 多文档/多事件关联 | 40 | 某次决策的依据、影响范围与后续任务 |
| 时间与版本更新 | 40 | 当前规定与上个月规定分别是什么 |
| 候选、确认和冲突 | 40 | 提议改配置，确认前后分别如何回答 |
| 无答案、否定与干扰 | 40 | 数据中没有的审批、已否定的错误说法 |
| 真实团队任务 | 40 | 整理发布检查清单、交接项目、回答变更依据 |

治理/故障测试另覆盖多个 workspace 的碰撞数据、重复事件、撤回、删除与 Worker 中断，不计入上述 300 题的普通问答分母。

建议按 workspace、项目或整段事件历史划分开发/验证/测试集，例如 20%/20%/60%。同文档的近义问题不跨集合泄漏；需要时间推理的测试只提供查询时刻之前允许看到的事件。规模足够后扩大冻结测试集，以目标差异和置信区间宽度决定样本数。

每个用例保存 question、as_of、workspace、input_history、预定确认/撤回事件、gold_facts、必要证据、允许输出、禁止输出和业务断言。生产数据先按企业授权和脱敏策略制备。

## 6. 三条公平对比轨道

### 6.1 轨道 A：受控检索

向各系统提供相同的已授权、已确认语料，同样的源 ID；使用相同回答模型、提示词、最终上下文 token 预算、问题和硬件上限。尽可能使用相同 Embedding；不支持时明确作为受控变量差异报告。

允许各系统使用自己的分块、索引和图构建，测完整检索机制；另外可以增加固定 chunk 的消融实验隔离检索器差异。图构建和预计算摘要的时间/费用必须计入导入成本。

只比较返回上下文与同一回答模型的结果。某个系统只能返回最终答案时，将其放入端到端轨道，不能把它生成的答案作为“原始检索证据”交给同一读者，从而多获得一次未计量推理。

### 6.2 轨道 B：原生记忆生命周期

按时间向各系统输入同一事件流：明确事实 → 未确认提议 → 授权确认 → 来源更新 → 冲突 → 撤回/删除。分别在每一步提问，测抽取、审批、当前值、来源与权限。

人工/服务确认脚本根据预先标注的输入事件编制，在看到系统测试答案前冻结。不能看金标准答案后只替本系统挑出正确候选来确认；应保留误抽取、未抽取、确认耗时和拒绝结果。

本系统要求候选确认，若另一系统自动发布，不应在普通问答表中偷偷把两种发布策略视为等价。分别报告原生策略与“加统一审批适配层”的结果，并记录审阅/适配成本。

### 6.3 轨道 C：完整 Agent 任务

使用同一 Agent 运行时、基础模型、工具权限、任务输入、最大轮数和费用预算，仅替换上下文服务。设置无记忆和简单混合检索基线。

报告任务成功、错误行为、返工、耗时、模型费用和人工审阅时间。支持各系统推荐配置的“最佳配置轨道”可以另跑，但与受控轨道分开，不能混排。

## 7. 开源评测资源的复用

| 资源 | 适合复用的内容 | 对当前需求的边界 |
| --- | --- | --- |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 信息提取、跨会话、知识更新、时间推理和无答案评测；官方评分脚本 | 以长期交互记忆为主，不替代企业权限与确认测试 |
| [LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2) | 企业/网页 Agent 历史、状态变化与工作流知识，关注准确性及查询延迟 | 含多模态轨迹；文本限定子集必须单独标注，不冒充完整官方结果 |
| [LoCoMo](https://github.com/snap-research/locomo) | 长对话及跨会话记忆实验 | 与本系统 workspace 事实治理不同，作为补充 |
| [BEIR](https://github.com/beir-cellar/beir) | 通用检索评估工具和数据格式 | 静态检索测量不能代表记忆更新/删除 |
| [Ragas](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/) | context precision/recall、faithfulness 等评测指标 | LLM 评分需固定版本与校准；企业权限用确定性断言 |
| [Cognee 的 BEAM 报告与工件](https://github.com/topoteretes/cognee/blob/main/cognee/eval_framework/beam/REPORT.md) | 理解和复现其已公开的检索、提示词和评分设置 | 不能直接用发布分数推断本企业数据上的胜负 |

优先调用这些项目已有的评分工具与适配接口，仅新增 ContextDB adapter、企业事件脚本、来源映射和权限断言。统计、数据格式和基础评分不用重复实现。

公开记忆题可能默认输入事实可直接使用，当前产品则要求自动抽取候选经确认。跑此类 benchmark 时要明确采用“全部输入已授权语料”的受控轨道，还是增加冻结确认脚本的生命周期轨道；不能偷偷关闭产品规则后宣称测得生产配置。

## 8. 如何解读 Cognee 的公开分数

Cognee 官方 BEAM 技术报告区分主要结果与探索结果：100K 设置使用保留会话重复评测，10M 设置在同一批问题上选择检索配置，因此被作者标为探索性结果。这表明对比时必须查看划分、路由与提示词，不能只抄一个分数。[官方技术报告](https://github.com/topoteretes/cognee/blob/main/cognee/eval_framework/beam/REPORT.md)

本项目应复现可用配置并在冻结企业测试集上重新运行。若公开题目的类型标签被用于路由，需要给所有系统相同信息；更贴近生产的做法是只给问题文本，由路由器推断并计入其成本。

不能根据架构图提前宣布“Cognee 多跳一定更好”或“PG 方案一定更快”。图检索可能帮助某些关联题，这是待验证假设；本系统的确认和撤回设计也只是待验证能力，不是已测得优势。

## 9. 实验控制与统计

每次运行保存 commit/tag、依赖锁、部署拓扑、硬件、数据 hash、模型/Embedding/裁判版本、prompt、随机种子、检索配置、预算和超时。对每个系统给相同调优次数或费用上限，只在开发/验证集调参。

冷启动和热缓存分别测量。入库、查询、回答、评分费用分开记录；评分费用不计入线上单次查询成本，但计入评测预算。内部模型调用无法观测的部分标记未知，不当作零费用。

最终测试至少重复多个推理轮次观察模型波动；同一道题重复执行不增加独立题目数。质量差异用配对分析，按 workspace/会话等独立单位做聚类 bootstrap 区间，避免把同一历史中的高度相关问题当作完全独立样本。报告分组结果，不能用平均分掩盖版本更新或冲突类失败。

错误、超时和空结果纳入全部被指派任务的成功率分母；质量评测可补充成功请求子集，但必须单列。p95/p99 与负载、超时率一起展示，不能通过丢掉超时请求让延迟看起来更低。

## 10. 成本和选型规则

```text
周期总成本 = 文档初次处理 + 增量处理 + 查询/回答模型 + 基础设施
           + 人工确认/返工 + 接入与维护成本

每个成功任务成本 = 同一周期纳入的总成本 / 成功任务数
```

人工成本未能货币化时报告分钟/百条候选和平均确认等待，不与 API 费用强行混为一个精确金额。建设与迁移成本分别列出，说明摊销周期。每千次查询同时报告语料规模和日增量，否则重预计算方案与轻写入方案不可比。

建议的决策顺序：

1. 原生或加适配后的方案是否通过企业正确性门槛。
2. 相比无记忆及简单检索，是否带来可复现的任务成功提升。
3. 在相同预算下是否位于质量、延迟、成本的合理取舍范围。
4. 缺失能力能否通过少量适配补齐，还是需要重做核心生命周期。
5. 如果开源系统在满足门槛后效果和总成本更合适，优先复用该系统或其组件。

不预设“必须自研胜出”。也不设未经业务确认的通用合格线，例如一概要求 90% Recall；阈值在验证集和业务风险评审后冻结，在测试前确定。
